Wireframe-level UX specification

Screen by screen, state by state

Every screen below is drawn from the actual decision-tree content and admin-page specification already committed to this repository — real prompts, real Hindi strings, real node IDs — not placeholder copy. Each wireframe is annotated with the specific interaction states (default, loading, error, empty) and accessibility behaviour a real implementation must handle, going one level more concrete than the prose descriptions in the PRDs.

Extends docs/PRD-V2-RUST-PLATFORM.md §5 (design system), §11 (admin pages) and docs/PRD-V3-COMPREHENSIVE-EXPANSION.md §V5–V6. Content sourced from rust/crates/core-domain/src/tree_v1.json.

2. Question flow

Real content from node student_ordinary_residence_choice. Options are single-tap buttons, not radio-plus-submit — one action per screen, per the minimalism rule in PRD v3 §V5.

Question default
Would you rather register at your native/family address, or at your hostel/mess address?
This is your choice to make either way — we're only explaining the two options and what each requires.
← Back
Keyboard/a11y: options are a role="group" of real <button>s labelled by the visible prompt; first option receives focus on node change (visible focus ring, shown here on option 1) so keyboard/switch users never lose their place. Progress bar exposes role="progressbar" with aria-valuenow; the numeric percentage is announced via a visually-hidden aria-live="polite" region, not the bar itself (a progress bar's fill alone is not reliably announced by screen readers).
Question answer in flight
Would you rather register at your native/family address, or at your hostel/mess address?
State: the tapped option shows an inline spinner and every option disables (not just the tapped one) to prevent a double submission race — the request is a single small JSON POST to /v1/sessions/answers, so this state is typically visible for well under 300 ms on a 4G connection (PRD v2 §9 latency SLO) but must still render correctly on 2G.

3. Loading & error states

The three states every screen in this product must handle explicitly — not just the "happy path" shown above.

First load skeleton
Why a skeleton, not a spinner: the server-rendered Leptos page (PRD v2 §6.6) ships the first node's real markup on first paint — no skeleton is actually needed for node 1. This skeleton state only occurs on a slow reconnect mid-session, so it should be rare in practice and is shown here precisely because it's an easy state to forget to design.
Network error offline / timeout
Would you rather register at your native/family address, or at your hostel/mess address?
⚠
Couldn't reach VoteAssist. Your answers so far are safe.
Try again
Recovery guarantee: because session state lives client-side as the opaque token (PRD v2 §8, §6.3), a dropped connection never loses progress — retry simply re-sends the same token. Copy says this explicitly ("your answers so far are safe") rather than leaving the user to guess.

Empty states teach, not just apologise: the copy corrects a real, common misconception (Aadhaar ≠ EPIC) rather than a generic "no results found."

Trust hierarchy in the layout: the deep-link button is the single highest-contrast element on the screen (accent-filled, everything else outlined or plain), and it is explicitly labelled as leaving VoteAssist — the product's entire premise is "guidance ends here, the official action happens there," and the visual weight should say so before the copy does.

10. Admin — MCC control panel

PRD v2 §11 admin page 8 — a safety-critical surface, styled with deliberately less visual polish and more explicit confirmation than anything else in the console.

MCC panel 1 state active
Karnataka — Assembly election announced 12 days ago
Kerala
Tamil Nadu
Karnataka active: proactive bot broadcasts are throttled and carry an extra neutrality disclaimer. Toggling this off requires typing "END MCC" to confirm — closing a window is always an explicit human action.
Deliberate friction: most admin actions in this console are one click; this one is not, on purpose — it's the single control surface where a wrong click has the highest real-world consequence (PRD v2 §11 admin page 8).
